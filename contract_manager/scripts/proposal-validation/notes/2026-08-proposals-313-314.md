## Part 2 summary (complete)

Tooling: `contract_manager/scripts/proposal-validation/`.

Proposal #314 contains 99 instructions = 33 chains x
{`UpgradeContract`, `SetDataSources`, `SetWormholeAddress`}, 19 mainnet + 14
testnet. Results:

- guardian set matches the canonical `pro-compatible-production` set on
  **33/33** chains, order-exact, all at guardian set index 0;
- each target Wormhole contract's `chainId()` equals the chain its governance
  message is addressed to — 33/33;
- `SetDataSources` payloads byte-identical on 33/33 (Pythnet, chain 26);
- the wormhole address genuinely changes on 33/33 (19-guardian -> 5-key);
- a live production Pyth Pro VAA verifies `valid=true` on **33/33**;
- all 5 routers observed signing live, each at its expected guardian index.

Quorum was the subtle risk: two implementations exist in this repo,
`ReceiverMessages.quorumThreshold` (2/3 -> 4-of-5) and
`ReceiverImplementationHalf.quorumThreshold` (n/2+1 -> 3-of-5). Pyth Pro signs
3-of-5, so the 2/3 variant would reject every price update. The replay confirms
the deployed contracts use the majority rule.

## Part 1: contract build validation

_In progress. Findings appended below as they are established._

### 1A — build from source and match the proposal — **EVM: PASS**

Proposal #314 carries 33 `UpgradeContract` actions, each naming an
already-deployed implementation address (31 distinct addresses; `bsc`,
`cronos` and `sonic_evm_testnet` share `0xf777…d7ba`, which is just the same
deployer/nonce landing on the same address on three chains).

**All 33 deployed implementations are the same contract.** Fetched via
`eth_getCode`: every one is 24067 bytes. Raw blobs differ, but the differences
are confined to five 20-byte regions at offsets 3017, 3081, 4291, 4355, 4479 —
each holding the contract's *own address*. Those are the low 20 bytes of the
five 32-byte immutable slots forge reports for `PythUpgradable`
(`immutableReferences` at 3005/3069/4279/4343/4467), i.e. the UUPS `__self`
immutable. Normalising those slots collapses all 33 to a single digest.

**Build.** `forge build` in `target_chains/ethereum/contracts`, solc 0.8.29,
`evm_version = paris`, optimizer on, 200 runs (all from `foundry.toml`). The
on-chain CBOR trailer ends `64736f6c634300081d`, confirming solc 0.8.29 was
used for the deployed code too.

**Result — executable bytecode matches exactly:**

| | keccak256 of runtime code, immutables zeroed, metadata trailer stripped |
| --- | --- |
| built at `4739bbcb8` (and at HEAD `8b187ddf6`) | `645c9c8bfbfa3b6d5b7dcbef934f3dee99e1d544dde61933e5b0adedb9d18537` |
| deployed, all 33 chains | `645c9c8bfbfa3b6d5b7dcbef934f3dee99e1d544dde61933e5b0adedb9d18537` |

Every executable byte of the proposed implementation is reproduced from source.

**Which commit.** `4739bbcb8` ("feat(evm): allow SetWormholeAddress without
dual-verify", #3973) is the most recent commit touching any of the 35 sources
in the compilation unit, so it and HEAD build identically. The preceding such
commit, `213ad6788`, builds to a *different* length (24498 vs 24067) — so the
deployed code corresponds specifically to source at or after `4739bbcb8`, not
to anything earlier.

**Known limitation — metadata trailer.** The 32-byte IPFS metadata hash in the
CBOR trailer differs between my build and the deployed code:

| | |
| --- | --- |
| deployed (identical on all 33) | `42c1115c…e6455` (CID `QmSqENHNUk8iS25RSKrh4An99FuDuYCZ7scY1z11TmvHkG`) |
| my build | `0c16023d…af16c` (CID `QmP9q4p9gSAoeof9MSr1g6JtCWQPChuiPCQML8oQyutYAF`) |

This region is appended after the runtime code and never executed. The hash
covers the metadata JSON, which includes source *paths* and the full resolved
settings, so it is sensitive to the build environment (dependency tree layout,
remapping set) even when every compiled byte is identical — and my dependency
tree was assembled by hand rather than by `pnpm install`, since npm rejects the
workspace's `catalog:` protocol. Attempts to obtain the original metadata for a
byte-exact comparison all failed: the implementations are not verified on
Sourcify, not verified on the Blockscout instances checked (etherlink, soneium),
and public IPFS gateways refuse the CID. Treat 1A as "executable code proven
identical", not "byte-exact including metadata".

Worth noting the deployed metadata trailer is **identical across all 33
chains**, so all 33 came from one canonical build.

#### The change: `setWormholeAddress` loses its dual-verify

Before (`v1.4.6`), setting a new Wormhole address was self-checking. The
contract set the new address and then re-parsed and re-verified *the very same
governance VAA* through the **new** Wormhole contract, requiring that it be
valid, come from a valid governance data source, carry the expected sequence,
decode to a `SetWormholeAddress` action, and name the same new address.

After (`4739bbcb8`) that is replaced by two sanity checks: the new address must
be non-zero and must have code.

**Why it had to go.** The dual-verify demanded that the *new* Wormhole contract
be able to verify the governance VAA authorising the switch. That VAA is
emitted through the standard Wormhole core bridge and is signed by the
19-guardian Wormhole set, whereas the incoming Pyth Pro contract only knows the
5 routers. The old code would therefore have reverted on exactly this
migration — the dual-verify makes a guardian-set change impossible by
construction. Removing it is what makes proposals #313/#314 executable at all.

**What is given up.** The removed check was the guarantee that you cannot point
a Pyth contract at a Wormhole contract unable to verify Pyth governance.
Because *all* future governance is verified through `wormhole()`, a later
`SetWormholeAddress` naming a wrong-but-code-bearing address now permanently
bricks both governance and price updates on that chain, with no recovery path.
Post-upgrade the only thing standing between the contract and that state is the
correctness of the multisig proposal itself. This is a deliberate, accepted
trade — but it is the single most consequential line in the proposal and should
be a conscious sign-off, not an incidental one.

#### Ordering — checked, correct

Per chain the proposal is ordered `UpgradeContract` → `SetDataSources` →
`SetWormholeAddress`, on **33/33 chains** (instructions 1-3, 4-6, … in proposal
order). That order is required: run under the *old* implementation,
`SetWormholeAddress` would hit the dual-verify and revert. The new
implementation must be in place first.

The order is also enforced on-chain — `verifyGovernanceVM` rejects
`vm.sequence <= lastExecutedGovernanceSequence()`. Two consequences:

- Out-of-order execution fails *safely*: submitting `SetWormholeAddress` first
  reverts under the old implementation's dual-verify, so nothing is consumed.
- The check is `<=`, i.e. strictly increasing but **not** consecutive. So a
  *skipped* instruction can never be applied afterwards — its sequence is
  already stale. If `UpgradeContract` and `SetWormholeAddress` landed but
  `SetDataSources` were skipped, that chain would end up verifying via Pyth Pro
  while still trusting only the old data sources, rejecting every new price
  update, and `SetDataSources` could never be replayed. **All three
  instructions per chain must be executed, in order, with none skipped.**

#### `SetDataSources` is a real change, not a no-op

All 33 chains currently carry **three** data sources:

```
chain 1  (solana)  0x6bb14509a612f01fbbc4cffeebd4bbfb492a86df717ebe92eb6df432a3f00a25
chain 26 (pythnet) 0xf8cd23c2ab91237730770bbea08d61005cdda0984348f3f6eecb559638c0bba0
chain 26 (pythnet) 0xe101faedac5851e32b9b23b5f9411a8c2bac4aae3ed4dd7b811dd1a72ea4aa71
```

The proposal replaces them with a **single** source — chain 26, emitter
`0x507974686e6574…` ("PythnetPythnetPythnetPythnetPyth") — which is exactly the
emitter observed on the live Pyth Pro VAAs in part 2. So the three legacy
emitters are retired in the same operation.
