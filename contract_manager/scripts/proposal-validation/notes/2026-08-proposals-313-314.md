the deployed contracts use the majority rule.

### 1A — build from source and match the proposal — **EVM: PASS**

| | |
| --- | --- |

#### The change: `setWormholeAddress` loses its dual-verify

Before (`v1.4.6`), setting a new Wormhole address was self-checking. The
contract set the new address and then re-parsed and re-verified *the very same
governance VAA* through the **new** Wormhole contract, requiring that it be
valid, come from a valid governance data source, carry the expected sequence,
decode to a `SetWormholeAddress` action, and name the same new address.

After (`4739bbcb8`) that is replaced by two sanity checks: the new address must
be non-zero and must have code.

**Why it had to go.** The dual-verify demanded that the *new* Wormhole contract
be able to verify the governance VAA authorising the switch. That VAA is
emitted through the standard Wormhole core bridge and is signed by the
19-guardian Wormhole set, whereas the incoming Pyth Pro contract only knows the
5 routers. The old code would therefore have reverted on exactly this
migration — the dual-verify makes a guardian-set change impossible by
construction. Removing it is what makes proposals #313/#314 executable at all.

**What is given up.** The removed check was the guarantee that you cannot point
a Pyth contract at a Wormhole contract unable to verify Pyth governance.
Because *all* future governance is verified through `wormhole()`, a later
`SetWormholeAddress` naming a wrong-but-code-bearing address now permanently
bricks both governance and price updates on that chain, with no recovery path.
Post-upgrade the only thing standing between the contract and that state is the
correctness of the multisig proposal itself. This is a deliberate, accepted
trade — but it is the single most consequential line in the proposal and should
be a conscious sign-off, not an incidental one.

#### Ordering — checked, correct

Per chain the proposal is ordered `UpgradeContract` → `SetDataSources` →
`SetWormholeAddress`, on **33/33 chains** (instructions 1-3, 4-6, … in proposal
order). That order is required: run under the *old* implementation,
`SetWormholeAddress` would hit the dual-verify and revert. The new
implementation must be in place first.

The order is also enforced on-chain — `verifyGovernanceVM` rejects
`vm.sequence <= lastExecutedGovernanceSequence()`. Two consequences:

- Out-of-order execution fails *safely*: submitting `SetWormholeAddress` first
  reverts under the old implementation's dual-verify, so nothing is consumed.
- The check is `<=`, i.e. strictly increasing but **not** consecutive. So a
  *skipped* instruction can never be applied afterwards — its sequence is
  already stale. If `UpgradeContract` and `SetWormholeAddress` landed but
  `SetDataSources` were skipped, that chain would end up verifying via Pyth Pro
  while still trusting only the old data sources, rejecting every new price
  update, and `SetDataSources` could never be replayed. **All three
  instructions per chain must be executed, in order, with none skipped.**

#### `SetDataSources` is a real change, not a no-op

All 33 chains currently carry **three** data sources:

```
chain 1  (solana)  0x6bb14509a612f01fbbc4cffeebd4bbfb492a86df717ebe92eb6df432a3f00a25
chain 26 (pythnet) 0xf8cd23c2ab91237730770bbea08d61005cdda0984348f3f6eecb559638c0bba0
chain 26 (pythnet) 0xe101faedac5851e32b9b23b5f9411a8c2bac4aae3ed4dd7b811dd1a72ea4aa71
```

The proposal replaces them with a **single** source — chain 26, emitter
`0x507974686e6574…` ("PythnetPythnetPythnetPythnetPyth") — which is exactly the
emitter observed on the live Pyth Pro VAAs in part 2. So the three legacy
emitters are retired in the same operation.

### How the migration is meant to run

From `programs/pyth-solana-receiver/tests/test_migrate_guardian_set.rs`, which
rehearses it against the real mainnet binary: **upgrade the program, close every
guardian set, re-run `initialize`**, then relay a production router VAA through
the upgraded bridge.

Reading the code, the mechanism is:

- `close_guardian_set` closes the set named by `config.guardian_set_index` and
  decrements that index. Starting from 7 that is eight calls to reach zero.
  Its only guard is that the set being closed contains one of the 34
  `LEGACY_GUARDIANS` — which is what stops it being pointed at the router set.
- `initialize` then declares `init_if_needed` on `config` but plain `init` on
  guardian set 0 and on the fee collector. That is why *every* set must be
  closed first, index 0 included: `init` fails if the account already exists.
  It writes `guardian_set_index: 0` and installs the hardcoded router set.

Three properties worth being explicit about:

1. **Both instructions are permissionless.** `close_guardian_set` says so in
   its own doc comment; `initialize` requires only `payer: Signer` and performs
   no authority check. Neither is in proposal #313 — the proposal only performs
   the program upgrade and the receiver config changes. The guardian switch
   happens *afterwards*, and anyone can drive it.
2. **That is far less alarming than it sounds**, because the set `initialize`
   installs is a compile-time constant. A third party can influence *when* the
   migration happens, not *which keys* land. The risk is availability and
   ordering, not key substitution.
3. **There is a window with no usable guardian set.** Between the first
   `close_guardian_set` and a successful `initialize`, the bridge cannot verify
   VAAs, so price updates on that chain stall. The window is permissionlessly
   openable the moment the upgrade lands. Worth knowing operationally; it is the
   SVM analogue of the ordering constraint on the EVM side.

**Now verified — the rehearsal test was run, and it passes.** See "SVM
migration rehearsed end to end" below.

### The observed instruction sequence

Extracted from the program logs, this is what the test actually executes:

```
LegacyInitialize                     bring up the pre-migration bridge
InitEncodedVaa / WriteEncodedVaa / VerifyEncodedVaaV1
LegacyGuardianSetUpdate  x7          replay the 7 real mainnet upgrade VAAs -> set 7
Initialize                           (receiver)
LegacyCloseGuardianSet   x8          close sets 7,6,5,4,3,2,1,0
LegacyInitialize                     re-init: installs the 5 routers at index 0
PostUpdate                           production Pyth Pro VAA -> receiver
```

Two details line up with what is live on-chain and confirm the reading of the
code above: it reaches **guardian set index 7**, exactly matching
`config.guardian_set_index = 7` observed on both Solana and Fogo; and it takes
exactly **eight** `LegacyCloseGuardianSet` calls to get from 7 down to 0.

The final `VerifyEncodedVaaV1` + `PostUpdate` pair is the SVM analogue of the
33/33 `parseAndVerifyVM` replay on EVM: a **production Pyth Pro router VAA is
verified by the migrated bridge and posted into the receiver**. That is the
end-to-end property that matters, and it holds.

### The fee-collector concern is resolved

The earlier worry was that `initialize` declares plain `init` on the fee
collector, which would collide with the one already on mainnet. It does not,
and the test genuinely exercises the case: it calls `LegacyInitialize` twice
with no close of the fee collector in between, so the second call runs over an
existing one.

The mainnet state has the same shape the test produces — on **both** chains:

```
fee_collector PDA 3L5jSRQacMwwByK56zasYvKGpL722XgswvtjztbjfVTu
  solana: lamports=890880 owner=SystemProgram data_len=0
  fogo  : lamports=890880 owner=SystemProgram data_len=0
```

(890880 is the rent-exempt minimum for a zero-length account.)

### What this still does not cover

- It runs on `solana-program-test`, a simulated ledger seeded with the accounts
  the test creates. It is not a fork of full mainnet state, so an unrelated
  account colliding with a PDA the migration needs would not show up.
- The post-upgrade binary in the test is the **local** build. It matches the
  proposal buffer on size and section layout but is not byte-identical
  (platform-tools paths). Running the same test inside the pinned Docker image
  would close that last gap.
- Fogo is not separately rehearsed. It runs the same program from a
  byte-identical buffer and shows the same `guardian_set_index = 7` and the same

  inference, not a second test run.

| proposed implementation | **24067 bytes, digest `645c9c8b…`** | **24067 bytes, digest `645c9c8b…`** |

The proposed implementations on both Abstract chains are **ordinary EVM

The obvious worry — EVM bytecode deployed on a zkEVM that cannot execute it,
which would brick the chain on upgrade — does not hold. Calling `version()`
directly on the proposed implementations returns `1.4.6` on both Abstract
mainnet and testnet, matching the control call against Ethereum's proposed
implementation. The bytecode runs.

### Operational gotcha: `version()` does not change

The proposed implementation reports `version() == "1.4.6"` — and the 15 mainnet
chains **already** report `1.4.6` today. The string was not bumped for the
dual-verify removal.

So `version()` cannot be used to confirm the upgrade landed. Post-execution
verification has to compare implementation bytecode (or read the ERC-1967 slot
and check the address), not the version string. `check_evm_bytecode.py` reports
both, and the digests differ cleanly: `60e6a3d94fd4260b…` before,
`645c9c8bfbfa3b6d…` after.
